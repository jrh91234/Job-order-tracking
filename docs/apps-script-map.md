# Apps Script Deployment Map

ระบบนี้ใช้ Google Apps Script **2 โปรเจกต์แยกกัน** เอกสารนี้คือแหล่งอ้างอิงหลัก
ว่าอะไรอยู่ที่ไหน เปิดหาอย่างไร และห้ามทำอะไร

> อ่านไฟล์นี้ก่อนแตะโค้ดฝั่ง Apps Script ทุกครั้ง

## ทำไมต้องแยก 2 โปรเจกต์

Apps Script รวมทุกไฟล์ในโปรเจกต์เดียวกันไว้ใน scope เดียว **ถ้ามีฟังก์ชันชื่อซ้ำกัน
ตัวที่โหลดทีหลังจะทับตัวแรกแบบเงียบ ๆ ไม่มี error** ทั้งสองโปรเจกต์ต่างก็ต้องมี `doPost`
ของตัวเอง จึงอยู่ร่วมโปรเจกต์กันไม่ได้

เคยเกิดขึ้นจริงมาแล้ว: โค้ดบันทึกเหตุการณ์ถูกวางรวมในโปรเจกต์ของหน้าลงยอด `doPost`
ทับกัน ทำให้การลงยอดแมนนวลหยุดเข้าแท็บ `ยอดผลิต` ไปกว่า 1 เดือนโดยไม่มีใครรู้
(รายละเอียดใน PR #41)

## แท็บ `Incidents`

```
ID = "2026-08-13_21_5_All"  (วันผลิต_ชั่วโมง_ไลน์_รุ่น)
คอลัมน์: ID | Date | Hour | Line | Model | JobOrder
         | Category | CategoryText | Notes | Time | Shift
```

`Shift` เพิ่งเพิ่มเข้ามา แถวเก่าจะว่างไว้ ไม่ต้องไปเติมย้อนหลัง
เพราะหน้าจออนุมานกะจาก `Hour` ให้เองอยู่แล้ว ด้วยกติกาเดียวกับการอ่านบาร์โค้ด
(`00:00-07:59` และ `20:00-23:59` คือกะดึก) ต่างกันแค่ไม่ต้องเลื่อนวัน
เพราะ `Date` ของเหตุการณ์เป็นวันผลิตอยู่แล้ว ไม่ใช่เวลานาฬิกาดิบ

ตอนกรอง หน้าจอจะให้ **การโอนยอดข้ามกะทับกะที่อนุมานได้อีกชั้นเสมอ**
แม้แถวนั้นจะมีค่า `Shift` เก็บไว้แล้วก็ตาม เพราะการโอนมักเกิดขึ้นทีหลัง
เหตุการณ์ตอน 21:00 ของไลน์ที่โอนเข้ากะเช้าแล้วจะได้ไม่ค้างอยู่ในกะดึก
ยกเว้นเหตุการณ์ที่บันทึกว่ากระทบ `All` ไลน์ ซึ่งไม่ผูกกับไลน์ใด จึงไม่ถูกโอน

## แท็บ `Manpower`

กำลังคนรายไลน์ แยกตามกะ 1 แถว = 1 วัน + 1 กะ + 1 ไลน์

```
ID = "2026-08-10_Day_Line 5"
คอลัมน์: ID | Date | Shift | Line
         | Assembler | Feeder | Leader | Total
         | OTAssembler | OTFeeder | OTLeader | OTTotal | UpdatedAt
```

คอลัมน์ `OT*` คือกำลังคนช่วงที่ทำเกิน 8 ชั่วโมงสุทธิ ซึ่งมักเหลือคนน้อยกว่าช่วงปกติ
สคริปต์เขียนโดยอิงชื่อคอลัมน์ในหัวตารางจริง แท็บที่สร้างไว้ก่อนมีคอลัมน์ OT จึงใช้ต่อได้
โค้ดจะเติมหัวคอลัมน์ที่ขาดให้เอง แถวเก่าเว้นว่างในคอลัมน์ใหม่โดยไม่ถูกแตะต้อง

ค่าที่เป็นข้อความถูกเขียนโดยนำหน้าด้วย `'` เพื่อไม่ให้ Sheets แปลงชนิดเอง
(บทเรียนจากคอลัมน์ `Date` ใน PR #38 และ `Time` ใน PR #47)

หน้าจอใช้ตัวเลขนี้คำนวณ **PCS/คน/ชม.** จาก man-hours จริง

```
PCS/คน/ชม. = ยอดสแกน ÷ (ประกอบช่วงปกติ × ชม.ปกติ + ประกอบช่วง OT × ชม. OT)

ชม.ปกติ = min(ชั่วโมงสุทธิ, 8)
ชม. OT  = max(0, ชั่วโมงสุทธิ − 8)
```

เกณฑ์ 8 ชั่วโมงตรงกับ `OT_THRESHOLD_NET_HOURS` ใน `scr/ชั่วโมงทำงาน.js`
ถ้ามีชั่วโมง OT แต่ยังไม่ได้กรอกคนช่วง OT ระบบถือว่าคนเท่าเดิม
(ให้ผลเท่าสูตรเดิมทุกประการ ตัวเลขย้อนหลังจึงไม่เพี้ยน) และขึ้นป้ายเตือนไว้ในตาราง

ชั่วโมงทำงานสุทธิ = ชั่วโมงที่มีการสแกนจริง หักเวลาพักตาม `BREAK_RULES` ชุดเดียวกับ `scr/ชั่วโมงทำงาน.js`
(12:00-13:00, 17:00-17:30, 00:00-01:00, 05:00-05:30) กะเต็ม 12 ชั่วโมงจึงคิดเป็น **10.5 ชั่วโมง**
ถ้าแก้กติกาเวลาพัก ต้องแก้ทั้งสองที่ให้ตรงกัน ไม่งั้นตัวเลขสองฝั่งจะไม่ตรง

ตัวหารนับเฉพาะ `Assembler` ส่วน `Feeder` และ `Leader` ยังต้องกรอกและเก็บไว้ทุกครั้ง
แต่ถือเป็นกำลังสนับสนุน ไม่ใช่คนที่ผลิตชิ้นงานในไลน์ จึงไม่นำมาหาร
คอลัมน์ `Total` ในชีตยังเป็นผลรวมทั้ง 3 บทบาทตามเดิม ใช้ดูกำลังพลจริงหน้างาน

## แท็บ `ShiftTransfers`

การโอนยอดช่วงเวลาหนึ่งของไลน์เข้ากะที่ต้องการ 1 แถว = 1 วัน + 1 ไลน์ + 1 ช่วงชั่วโมง

```
ID = "2026-08-11_Line 5_20_22"
คอลัมน์: ID | Date | Line | FromHour | ToHour | TargetShift | Note | UpdatedAt
```

**ทำไมต้องมี** — ระบบตัดกะจากเลขชั่วโมงล้วน ๆ (`barcode.html` ราวบรรทัด 1383)
ตั้งแต่ 20:00 ถือเป็นกะดึกเสมอ พอกะเช้าทำ OT ลากยาวถึง 22:00 ยอดชั่วโมง 20:00-22:00
จะถูกนับเป็นกะดึกทั้งที่คนกะเช้าเป็นคนทำ และโผล่เป็นแถวกะดึกที่ไม่มีใครกรอกกำลังคน

แถวนี้ให้ผู้ใช้ระบุเองว่าช่วงไหนของไลน์ไหนต้องนับเข้ากะอะไร `FromHour` นับรวม
`ToHour` ไม่นับรวม (20 ถึง 22 คือถังชั่วโมง 20 กับ 21) และข้ามเที่ยงคืนได้

แกนชั่วโมงของกราฟและตารางรายชั่วโมงเดิมฮาร์ดโค้ดตามกะ (กะเช้า 08:00-19:00)
ชั่วโมงที่โอนเข้ามาจึงถูกนับใน KPI แต่ไม่มีช่องให้แสดง ตอนนี้แกนจะต่อชั่วโมงที่โอนเข้า
และชั่วโมงที่มีการสแกนจริงเพิ่มให้ตามลำดับเวลา พร้อมกำกับ `⤵` บนหน้าจอ
และ `(โอนเข้า)` ในรายงาน PDF

หน้าจอเขียนทับกะที่ `processedScans` จุดเดียวหลังแปลงข้อมูลดิบเสร็จ
ทุกอย่างที่อยู่ถัดจากนั้น (ตัวกรองกะ, KPI, กราฟ, ตารางกำลังคน, รายงาน PDF) จึงเห็นกะเดียวกันหมด
**ไม่กระทบชีต `ยอดผลิต` และ `ชั่วโมงทำงาน`** ซึ่ง Apps Script อีกโปรเจกต์คำนวณแยกของตัวเอง

## แท็บ `IncidentDowntime` (AI สรุป Downtime)

ผล Downtime ที่ AI สรุปให้แต่ละเหตุการณ์ ทั้งที่บันทึกเอง และที่มาจากระบบแจ้งซ่อม
1 แถว = 1 เหตุการณ์ × 1 ไลน์ (เหตุการณ์ "ทุกไลน์" มีหลายแถว)

```
Key = "รหัสเหตุการณ์|ไลน์"
คอลัมน์: Key | ID | Line | Date | Minutes | Start | End | Confidence | Reason | Sig | By | UpdatedAt
```

- ฟังก์ชัน `summarizeIncidentDowntimes` ใน `gas_sync_incidents.js` ทำงานดังนี้
  - หาเหตุการณ์ที่แจ้งมาแล้วเกิน 60 นาที และยังไม่มีผล หรือผลเดิมคิดจากข้อมูลชุดเก่า (`Sig` ไม่ตรง เช่น แก้เวลา/ไลน์/ข้อความ)
  - อ่านสแกนจากชีตบาร์โค้ด (`BARCODE_SPREADSHEET_ID`) แล้วคำนวณช่วงหยุดสแกนรอบเวลาที่แจ้ง
  - ส่งข้อความที่แจ้ง + ช่วงหยุดให้ Gemini เลือก ทีละ วัน/กะ/ไลน์ เพื่อให้หลายเหตุการณ์ในช่วงเดียวกันแบ่งเวลากัน
- หน้า dashboard ได้ผลนี้ผ่าน `GET_INCIDENTS` (ฟิลด์ `downtimeSummaries`)
  - รายการที่มีผลจาก AI ใช้ค่านี้แทนกติกาจากสแกน และแสดง "🤖 AI สรุป" พร้อมเหตุผล
  - รายการที่ยังไม่มีผลใช้กติกาเดิมไปก่อน
- Gemini เรียกไม่สำเร็จ (ไม่มี key, โควตาเต็ม) ไม่เขียนอะไร รอบถัดไปจะลองใหม่เอง
- กลุ่มที่ไลน์สแกนต่อเนื่อง (ไม่มีช่วงหยุดรอบเวลาที่แจ้ง) และข้อความไม่มีตัวเลขเลย ระบบตัดสินเองเป็น 0 นาทีโดยไม่เรียก AI (`By` = `Rule`)

### โควตาและผู้ให้บริการ AI สำรอง

แต่ละกลุ่มจะลองผู้ให้บริการตามลำดับนี้ ตัวไหนตอบ HTTP 429 (โควตาเต็ม) หรือใช้ครบเพดานของวันแล้ว จะข้ามไปตัวถัดไปทั้งวัน
ตัวที่ยังไม่ได้ตั้ง key ใน Script properties จะไม่ถูกใช้

| ลำดับ | ผู้ให้บริการ | Script properties ที่ต้องตั้ง | เพดานต่อวัน (ค่าเริ่มต้น) | ค่าใช้จ่าย |
|---|---|---|---|---|
| 1 | Gemini Flash-Lite | `GEMINI_API_KEY` (เปลี่ยนโมเดลได้ด้วย `GEMINI_DOWNTIME_MODEL`) | 20 (`DOWNTIME_AI_MAX_PER_DAY`) | แผนฟรี |
| 2 | Gemini 2.5 Flash | `GEMINI_API_KEY` | 5 (เหลือโควตาให้การแปลรายงาน PDF) | แผนฟรี |
| 3 | Groq | `GROQ_API_KEY` (+ `GROQ_MODEL` ถ้าไม่ใส่ใช้ `llama-3.3-70b-versatile`) | 100 (`GROQ_MAX_PER_DAY`) | มีแผนฟรี |
| 4 | Claude (Anthropic) | `ANTHROPIC_API_KEY` (เปลี่ยนโมเดลได้ด้วย `ANTHROPIC_DOWNTIME_MODEL` ค่าเริ่มต้น `claude-opus-5-5`) | 50 (`ANTHROPIC_MAX_PER_DAY`) | เสียเงินตามการใช้งาน |
| 5 | OpenAI | `OPENAI_API_KEY` + `OPENAI_MODEL` | 50 (`OPENAI_MAX_PER_DAY`) | เสียเงินตามการใช้งาน |

- **ข้อจำกัดทั่วไป:**
  - Gemini: ไม่เกิน 4 ครั้งต่อรอบ เว้นระยะ 13 วินาทีระหว่างครั้ง (ลิมิตต่อนาทีของแผนฟรี) พอครบแล้วในรอบเดียวกันจะเรียกเจ้าถัดไป (Groq ฯลฯ) ต่อได้อีกไม่เกิน 10 ครั้งต่อเจ้า เว้นระยะ 3 วินาที
  - หยุดเรียก AI เมื่อรอบนั้นทำงานเกิน 4.5 นาที (Apps Script ตัดที่ 6 นาที) ที่เหลือทำรอบถัดไป
  - ทำกลุ่มล่าสุดก่อน และย้อนหลังแค่ 7 วัน
  - ทุกเจ้าเต็มแล้ว กลุ่มที่เหลือรอรอบหน้าหรือวันถัดไป
- **ชื่อโมเดล:** Groq ใช้ `llama-3.3-70b-versatile` ถ้าไม่ได้ตั้ง `GROQ_MODEL`; OpenAI ต้องตั้ง `OPENAI_MODEL` เอง
- **ชื่อโมเดลถูกเลิกใช้ (HTTP 404):** ระบบ Gemini/Groq/OpenAI จะดึงรายชื่อโมเดลที่ key นั้นใช้ได้ เลือกรุ่นที่ใกล้เคียงที่สุด (เช่น `gemini-flash-lite-latest`) แล้วจำไว้ใน Script property `downtime_ai_model_<id>` ถ้าตั้งชื่อโมเดลเองไว้ (`GEMINI_DOWNTIME_MODEL`, `GROQ_MODEL`, `OPENAI_MODEL`) ระบบจะใช้ชื่อที่ตั้งก่อนเสมอ ลบ property `downtime_ai_model_<id>` ทิ้งได้ถ้าอยากให้หาใหม่
- **ข้อความ error:** log จะแสดงข้อความจากผู้ให้บริการต่อท้าย เช่น `HTTP 404 (gemini-2.5-flash): models/... is not found`
- **ตรวจผลย้อนหลัง:** คอลัมน์ `By` ในแท็บ `IncidentDowntime` บอกว่าเจ้าไหนสรุป เช่น `AI:gemini-lite`, `AI:claude` หรือ `Rule` (ไลน์เดินต่อเนื่อง ตัดสินเองไม่ใช้ AI)
- **ดูลำดับที่ใช้ได้อยู่:** เปิด URL ของ Web App ตรง ๆ แล้วดูที่ `downtimeAi.providers`

### ตั้งค่าครั้งเดียว (เจ้าของโปรเจกต์ Incident Sync)

1. **Script property `GEMINI_API_KEY`:** ต้องตั้งไว้ (ตัวเดียวกับที่ใช้แปลรายงาน PDF)
2. **สิทธิ์ชีตบาร์โค้ด:** บัญชีที่ deploy ต้องมีสิทธิ์อ่านชีตบาร์โค้ด (ID ใน `BARCODE_SPREADSHEET_ID`)
3. **ตั้ง trigger:** เปิดโปรเจกต์ใน script.google.com → เมนู **Triggers (รูปนาฬิกา)** → **Add Trigger**
   - Function: `summarizeIncidentDowntimes`
   - Event source: **Time-driven**
   - Type: **Minutes timer**
   - Interval: **Every 15 minutes**
4. **ลองรัน (ไม่บังคับ):** เลือกฟังก์ชัน `summarizeIncidentDowntimes` ใน editor แล้วกด Run
   - Log (บรรทัดที่ขึ้นต้นด้วย `summarizeIncidentDowntimes:`) จะบอกว่าสรุปไปกี่รายการ เรียก AI กี่ครั้ง ใช้เจ้าไหน และเหลือกี่กลุ่มที่รอโควตา
   - ถ้าขึ้น `nothing to do (...)` ในวงเล็บจะบอกว่าอ่านเหตุการณ์ได้กี่รายการ อยู่ใน 7 วันล่าสุดกี่รายการ สรุปไปแล้วกี่รายการ และกี่รายการที่ยังแจ้งมาไม่ถึง 60 นาที
   - รอบแรกจะย้อนสรุปเหตุการณ์ 7 วันล่าสุด จากใหม่ไปเก่า ตามโควตาที่เหลือ

ไม่สร้าง trigger จากโค้ด เพราะต้องเพิ่ม scope `script.scriptapp` ซึ่งทำให้ Web App
ใช้งานไม่ได้จนกว่าเจ้าของจะกดอนุญาตใหม่

## หาโปรเจกต์ไม่เจอ ทำอย่างไร

1. เปิด https://script.google.com → เมนู **โปรเจกต์ของฉัน (My Projects)** จะเห็นทั้งสองตัว
   โปรเจกต์แบบ standalone จะ**ไม่ปรากฏ**ในเมนู ส่วนขยาย ของชีต จึงต้องเข้าทางนี้เท่านั้น
2. ถ้าจำชื่อไม่ได้ ให้เอา URL จากตารางด้านบนมาเปิดในเบราว์เซอร์
   ตัวบันทึกเหตุการณ์จะตอบ JSON ที่มี `project` และ `spreadsheet` บอกว่าเป็นตัวไหน
3. URL ที่ใช้งานอยู่จริงดูได้จาก `config.json` (บันทึกเหตุการณ์) และ `index.html` (ลงยอด)
   ถ้า URL ในรีโปไม่ตรงกับที่ deploy อยู่ ให้ยึดของที่ deploy แล้วอัปเดตรีโปตาม

## กฎที่ห้ามละเมิด

- **ห้ามรวมโค้ดสองโปรเจกต์เข้าด้วยกัน** ไม่ว่าจะสะดวกแค่ไหน เพราะ `doPost` จะทับกัน

  `isProductionEntryScriptUrl()` ที่จะปฏิเสธและเตือนอยู่แล้ว

- **ห้ามตั้งชื่อฟังก์ชันซ้ำกับที่มีอยู่ในโปรเจกต์เดียวกัน** โดยเฉพาะ `doGet` และ `doPost`

## Deploy อัตโนมัติของ Incident Sync

เมื่อ merge เข้า `main` และ `gas_sync_incidents.js` เปลี่ยน
workflow `.github/workflows/deploy-apps-script.yml` จะใช้ clasp push โค้ดเข้าโปรเจกต์ Incident Sync
แล้วอัปเดต deployment เดิม (URL ไม่เปลี่ยน) จากนั้นเรียก Web App เช็กว่ามี action `TRANSLATE`
โปรเจกต์ `KPI` (หน้าลงยอด) **ไม่ได้ผูกกับ workflow นี้**

ค่าเริ่มต้นของ Script ID และ Deployment ID ฝังไว้ใน workflow แล้ว (ไม่ใช่ความลับ) ที่ต้องตั้งจริงมีแค่ `CLASPRC_JSON`; Variable สองตัวด้านล่างใช้ทับค่าเริ่มต้นเมื่อ ID เปลี่ยน

ตั้งค่าที่ Settings → Secrets and variables → Actions ของรีโป

| ชนิด | ชื่อ | ค่า |
|---|---|---|
| Variable | `INCIDENT_SYNC_SCRIPT_ID` | Project Settings → รหัสสคริปต์ ของ Incident Sync |
| Variable | `INCIDENT_SYNC_DEPLOYMENT_ID` | Deploy → Manage deployments (ขึ้นต้น `AKfycb`) |
| Secret | `CLASPRC_JSON` | เนื้อไฟล์ `~/.clasprc.json` หลังรัน `clasp login` (มี refresh token ห้ามแชร์) |

ข้อควรรู้
- ต้องเปิด Apps Script API ที่ script.google.com/home/usersettings
- `clasp push` แทนที่ไฟล์ทั้งโปรเจกต์ด้วยชุดที่ stage ไว้ (`Code.js` + `appsscript.json`)
- ถ้าโค้ดขอสิทธิ์ใหม่ (เช่น `UrlFetchApp` ของ TRANSLATE) เจ้าของโปรเจกต์ต้องเปิดโปรเจกต์ใน editor แล้วรันฟังก์ชันใดก็ได้หนึ่งครั้งเพื่ออนุญาตสิทธิ์ Web App ถึงจะเรียกได้
- ถ้าตัวแปรหรือ secret ยังไม่ครบ workflow จะข้ามการ deploy พร้อมคำเตือน ไม่ล้มเหลว

## แจ้งซ่อมจาก Maintenance Management System

`GET_INCIDENTS` ใน `gas_sync_incidents.js` อ่าน `getBMJobs` แบบ read-only จาก
`tomtops43-png/Maintenance-Management-System` (URL ใน `js/config.js` ของต้นทาง)
และรวมเฉพาะ book `ENC` / พื้นที่ `ENC H9` กับเหตุการณ์เดิม ไม่เขียนงานแจ้งซ่อมลงแท็บ Incidents
และไม่แก้ไขต้นทาง งาน ASSY จะไม่ถูกรวมเข้ากับไลน์ H9

หนึ่ง MT Job เป็นหนึ่งเหตุการณ์ ณ ชั่วโมงที่แจ้ง (`timestamp`) ใช้เวลา Asia/Bangkok
วันผลิตเริ่ม 08:00; เวลาก่อน 08:00 นับเป็นวันผลิตก่อนหน้า `Line 5` แปลงเป็น `5`
เพื่อใช้ตัวกรองไลน์เดิม ข้อมูลแสดงเลขแจ้งซ่อม เครื่อง อาการ สถานะ และ downtime
ไม่กระจายรายการไปทุกชั่วโมงที่ซ่อม และไม่ใช้เวลา accept/finish แทนเวลาแจ้ง
รายการแสดงว่า “จากระบบแจ้งซ่อม” และแก้ไขจากระบบต้นทางเท่านั้น
หาก API ล้มเหลว หน้าจอแจ้งเตือนและเก็บรายการแจ้งซ่อมล่าสุดในเครื่องไว้

ต้อง deploy Incident Sync เวอร์ชันใหม่เพื่อเปิดใช้ โดยไม่แก้หรือ deploy โปรเจกต์ KPI
หาก Apps Script ขอสิทธิ์ `UrlFetchApp` ให้บัญชีที่ deploy อนุญาตสิทธิ์ก่อน
ทดสอบ mapping/API ด้วย `node tests/maintenance-incidents.test.cjs` จาก root ของ repo
การทดสอบนี้จำลอง Apps Script services; ต้องตรวจข้อมูลจริงหลัง deploy อีกครั้ง

หาก `GET_INCIDENTS` ส่ง `maintenanceError: MAINTENANCE_AUTHORIZATION_REQUIRED`
ให้บัญชีที่ใช้ deploy เปิดโปรเจกต์ Incident Sync ใน Apps Script editor
เลือกฟังก์ชัน `authorizeMaintenanceIntegration` แล้วกด Run และอนุญาตสิทธิ์
ฟังก์ชันอ่าน API อย่างเดียวและบันทึกจำนวนเหตุการณ์ใน Execution log
เสร็จแล้วโหลด dashboard ใหม่ ไม่ต้องเปลี่ยน URL หรืออนุญาตให้โปรเจกต์ KPI

Manifest ของ Incident Sync ระบุ OAuth scopes `spreadsheets` และ
`script.external_request` ไว้โดยตรง หลังอัปเดต scopes ให้บัญชีที่ deploy
รีเฟรช Apps Script editor แล้วรัน `authorizeMaintenanceIntegration` อีกครั้ง
และยอมรับสิทธิ์ที่เพิ่มมา หากยังไม่ผ่าน Execution log จะแสดงข้อผิดพลาดจริงของ Google
เฉพาะการรันใน editor; API สาธารณะยังแสดงรหัสสรุปโดยไม่เปิดเผยรายละเอียดภายใน
